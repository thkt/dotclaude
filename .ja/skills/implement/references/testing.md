# 今回必要なテストを選ぶ

テスト方針は対象 repo の方針に従う。以下は、変更が該当する失敗条件を持ち、既存検証では守れない場合にだけ使う例。正常な対照と狙った失敗を、必要な最小の層で確認する。

## UI E2E の待機と独立性

非同期に描画・再取得する UI の E2E テストを作成・更新するときだけ適用する。

- テスト間で可変データを共有するなら、各テストが独立に準備・後片付けできるか確認する。
- 表示や応答を待つときは、成功判定のための固定時間ではなく、操作に対応する状態・応答を待つ。不在を確認する前には、画面の準備完了を示す要素などの陽性条件を確認する。準備前にも対象が存在しない画面では、不在だけで成功としない。
- 再取得後も同じ値が表示され得るなら、表示値だけで更新完了とせず、その操作に対応する応答などを確認する。

既存テストが同じ失敗を防ぐ場合、非同期 UI を扱わない場合、撮影動画を読みやすくするためだけの間隔には適用しない。動画の間隔と、正しさの判定に使う待機を区別する。固定待機の一律禁止や、全 E2E の構造変更は求めない。

## 外部入力の拒否

| 項目           | 内容                                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 適用           | モデル応答や保存 JSON など、外部から来る値を受け入れる境界を変更するとき                                                           |
| 守る振る舞い   | 必要な形と対象 ID を満たす応答だけを現在の評価として扱う。構造の妥当性と、対象・権限などの意味上の照合は別の保証とする             |
| 対照と失敗入力 | 完全なレビュー応答に対し、必須項目の欠落、余分な項目、異なる `targetId` をそれぞれ与える                                           |
| 観測           | 正常応答は解析でき、不正応答は形の不正または対象不一致として拒否される。別の不正項目に先に遮られた結果を、狙った拒否の証拠にしない |
| 最小層         | 値の解析は関数テストで足りる。拒否後の保存・公開まで変える場合だけ、実際の入口を通す結合テストを選ぶ                               |
| 適用しない条件 | 外部入力の契約を変えない文書・表示の整理や、同じ不正条件を既存テストが既に検出する変更                                             |

## 停止時の副作用と記録保全

| 項目           | 内容                                                                                                                          |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 適用           | 評価失敗後の停止、修正の起動、保存履歴の更新など、失敗後の経路を変えるとき                                                    |
| 守る振る舞い   | 不正な再評価を現在の成功にせず、直前の完全な評価と原ログを残し、後続の修正・公開を起動しない                                  |
| 対照と失敗入力 | 有効な再評価が次へ進む条件と、前回指摘の更新が欠けた再評価を区別する                                                          |
| 観測           | 後者は `invalid_review` で停止し、前回の `reviewHistory` と作業を保ち、次の修正入力を作らない。例外が出たことだけでは足りない |
| 最小層         | 保存状態と後続起動を守るため、ホストの入口を通す結合テストが必要。純粋な解析の拒否はここで確認し直さない                      |
| 適用しない条件 | 停止経路や永続状態に触れない変更、既存の結合テストが同じ失敗後の結果を観測できる変更                                          |

## 対象版の変化

| 項目           | 内容                                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 適用           | 検証・評価・公開の前後で対象や根拠を再取得し、以前の成功を使う条件を変えるとき                                                                 |
| 守る振る舞い   | 確認後に対象が変われば、古い成功を現在の対象へ流用せず、保存済みの結果を保って停止する                                                         |
| 対照と失敗入力 | 同じ対象での再確認と、成功後に追跡ファイルを変更した再確認を比べる。変更を実際に検出対象へ加える                                               |
| 観測           | 前者は成功を再利用でき、後者は `target_changed_after_stop` を返し、以前の検証 state を変えない。別の設定不正による停止を版変化の検出と数えない |
| 最小層         | Git の対象と保存状態をまたぐ契約なので結合テストを選ぶ。純粋な比較関数だけでは成功の流用抑止を確認できない                                     |
| 適用しない条件 | 対象版の読み方や再利用条件を変えない内部整理、既存テストが同じ時点・対象・副作用を守る変更                                                     |

## 検査自体の空振り

| 項目           | 内容                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 適用           | テスト実行器、lint、評価などの成功判定や、検査対象の選択を変えるとき                                                            |
| 守る振る舞い   | 実行対象 0 件や未実行を成功と表示せず、検査が狙った不正入力を実際に拒否する                                                     |
| 対照と失敗入力 | 2 件の正常なテストを実行した結果に対し、空のテストファイル、skip、意図した不正応答を個別に与える                                |
| 観測           | 正常時だけ成功を案内し、0 件・skip は終了 1 と理由を示す。不正応答を与える確認では、狙った規則で失敗したことを確かめる          |
| 最小層         | 実行器の接続を変えるなら、小さな一時 fixture から公開入口を起動する。個別の純粋な検査規則なら、最初からプロセス全体を起動しない |
| 適用しない条件 | 検査定義を変えない通常の文書変更、検査の空振りが今回の失敗条件でない変更。全テストへの毎回の不具合注入はしない                  |
