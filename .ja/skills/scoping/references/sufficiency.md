# 十分性の判断

次に何を決めるかを先に特定し、6 つの問いで必要な根拠と不足を判断する。調査開始と実装開始に同じ情報量を要求しない。

全項目の回答を別の帳票へ保存しない。未確認を充足に含めず、重大な不足を他の項目で相殺しない。

現行実装・出典・合意が今回の判断にどう関係するかを確認する。モデルの自信、資料数、検索回数、書式の充足を根拠にしない。判断を左右する不足や根拠変更があれば依存作業を止め、影響する判断と再開条件を Issue または下書きへ残す。

| 観点         | 問い                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 目的         | 誰の何を改善し、次の判断と達成した状態を説明できるか                                                                     |
| 根拠         | 出典・対象版・鮮度・適用範囲を確認できるか                                                                               |
| 制約・代替案 | 判断を左右する制約・依存・代替案を確認したか。既存部品・標準 API・導入済みライブラリ・実装例の再利用と不足分を検討したか |
| 不確実さ     | 未確認事項で次の判断が変わり得ないか。影響しないとする根拠があるか                                                       |
| 整合         | 要求・事実・方針・合意の矛盾を解消したか                                                                                 |
| 権限         | 次の作業に必要な対象・範囲の合意と権限があるか                                                                           |

## 根拠と方針の整理

1. 次の判断を変え得る不明点を特定し、依頼・Issue の出典、関連文書、現在のコード・テスト・依存版・合意を照合する。過去の結論は今回への適用条件を確かめる。
2. 既存部品・標準 API・導入済みライブラリ・近い実装例との差を確認する。自前実装なら、既存機能で足りない理由と導入・保守の負担を示す。ロジックの要求では、入出力の制約、失敗条件、非同期処理、責任の境界を具体化する。
3. 事実・推測・提案・合意を区別する。出典・対象版・適用範囲・未確認事項、最小の解決案・完了条件・対象外・検証方法を、Issue または下書きから辿れるようにする。

## UI の要求がある場合

デザインシステム・Storybook・既存画面・テストから、今回使う部品の実装版・適用範囲・利用方針を照合する。要求に関係する状態・操作、キーボード・フォーカス・画面幅を確認し、部品単体の既存検証と、今回の配置・データ・遷移で追加する検証を分ける。

Storybook の存在を必須条件や合意の証拠にしない。既存資料で操作仕様が分からず判断を左右する場合は、その不足を解消してから UI 案を合意する。

## 質問と再評価

未回答・取消や部分的な回答を合意へ読み替えない。回答を得たら、その範囲を記録し、根拠と合意が次の判断に足りるか再評価する。

方針が決まった区切りで、要求・完了条件・検証方法、合意範囲と根拠、未解決事項を Issue・下書きへ反映する。質問ごとの転記や別の正本は作らない。

不足が残れば依存作業を止め、解消後に再評価する。同じ調査・質問で新しい根拠が得られなければ、確認済みのことと必要な判断を示して相談する。
