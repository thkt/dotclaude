# 十分性の判断

次に何を決めるかを先に特定し、6 つの問いで必要な根拠と不足を判断する。調査開始と実装開始に同じ情報量を要求しない。

全項目の回答を別の帳票へ保存しない。未確認を充足に含めず、重大な不足を他の項目で相殺しない。

現行実装・出典・合意が今回の判断にどう関係するかを確認する。モデルの自信、資料数、検索回数、書式の充足を根拠にしない。判断を左右する不足や根拠変更があれば依存作業を止め、影響する判断と再開条件を Issue または下書きへ残す。

| 観点         | 問い                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 目的         | 誰の何を改善し、次の判断と達成した状態を説明できるか                                                                     |
| 根拠         | 出典・対象版・鮮度・適用範囲を確認できるか                                                                               |
| 制約・代替案 | 判断を左右する制約・依存・代替案を確認したか。既存部品・標準 API・導入済みライブラリ・実装例の再利用と不足分を検討したか |
| 不確実さ     | 未確認事項で次の判断が変わり得ないか。影響しないとする根拠があるか                                                       |
| 整合         | 要求・事実・方針・合意の矛盾を解消したか                                                                                 |
| 権限         | 次の作業に必要な対象・範囲の合意と権限があるか                                                                           |

## 根拠と方針の整理

1. 次の判断を変え得る不明点を特定し、依頼・Issue の出典、関連文書、現在のコード・テスト・依存版・合意を照合する。過去の結論は今回への適用条件を確かめる。
2. 既存部品・標準 API・導入済みライブラリ・近い実装例との差を確認する。自前実装なら、既存機能で足りない理由と導入・保守の負担を示す。ロジックの要求では、入出力の制約、失敗条件、非同期処理、責任の境界を具体化する。
3. 事実・推測・提案・合意を区別する。出典・対象版・適用範囲・未確認事項、最小の解決案・完了条件・対象外・検証方法を、Issue または下書きから辿れるようにする。
4. 実装が前提に頼るときは、その前提と、前提を満たさない入力での動作を要求に書く。前提とは、実装が当てにしている入力や変換の性質で、外れるとエラーを出さずに誤った結果を返すものをいう。「一覧は整列済み」「ID は重複しない」「丸めても合計は変わらない」がその例で、これらに限らない。その入力を正しく扱うことを対象外にする場合も、誤った結果を出さない動作を要求に書き、前提が成り立つ範囲を添える。「扱わない」「拒否する」「元のまま返す」がその動作の例で、これらに限らない。前提だけを事実として書くと、実装はその外の入力を扱わず、独立レビューも Issue の記述を理由に必須の指摘にしない。

## UI の要求がある場合

デザインシステム・Storybook・既存画面・テストから、今回使う部品の実装版・適用範囲・利用方針を照合する。要求に関係する状態・操作、キーボード・フォーカス・画面幅を確認し、部品単体の既存検証と、今回の配置・データ・遷移で追加する検証を分ける。

Storybook の存在を必須条件や合意の証拠にしない。既存資料で操作仕様が分からず判断を左右する場合は、その不足を解消してから UI 案を合意する。

## 対象 repo の方針が課す手順

実装へ引き継ぐ要求では、対象 repo の README と開発方針が今回の変更に課す手順を列挙する。Issue 本文への手順に加えて、実装が変更する文書・PR 本文・公開・撮影への確認や承認も数える。Issue の完了条件を確かめる検証方法も、同じ一覧に入れる。workflow が自分で実行する検証は、`.dotagents.json` の `check`、`capture` の撮影、公開するときの CI (`ciChecks`) だけである。検証方法を判定するときは、commit 済みの `.dotagents.json` の `check` と `capture` を読む。対象 repo の文書が別の実行で行うと書いていても (`needs_host` など)、その 3 つのどれも実行しなければ、workflow が実行できない手順である。`/implement` の workflow は走り出すと人に問えず、独立レビューは方針どおりに行われていない手順を必須の指摘にする。扱いが決まっていない手順があると、実装を終えた後に `human-decision-required` で止まる。

列挙した手順とその判定は、質問と同じ回に一覧で人へ示し、Issue または下書きに書く。CLI が入っていることは、手順が実行できる根拠にならない。判定の記録が無いと、`/implement` は洗い出しが済んでいるかを見分けられない。

各手順を次の表で判定する。workflow が実行できない手順は、他の質問と同じ回に、§ workflow が実行できない手順の扱いの 3 つから 1 つを AskUserQuestion で人と合意する。

| 判定                    | 条件                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------ |
| workflow が実行できない | 参照先の手順書が無い。方針が指す文書と節を開いて確かめる                                               |
| workflow が実行できない | 必要な CLI が無い (`command -v <名前>` で確かめる)、または必要な権限が無い                             |
| workflow が実行できない | 人の操作が要る                                                                                         |
| workflow が実行できない | workflow が禁じる操作を要する。browser や server の起動、`.dotagents.json` の変更、worktree の外の編集 |
| workflow が実行できない | 検証方法で、設定された `check`・`capture`・公開するときの CI のどれも実行しないもの                    |
| workflow が実行できる   | 上のどれにもあたらない                                                                                 |

### workflow が実行できない手順の扱い

扱いは手順ごとに次の 3 つから 1 つ選び、その名前をそのまま Issue に書く。実行の中の誰かが後から実行する、という扱いは無い。check と撮影を受け持つ host も、実行の中にいる。それを合意すると、実装の後で修正とレビューが食い違い、`repair-no-progress` で止まる。代わりの手順を行うときは、扱いの欄に書き足さず、別の手順として一覧に加えて同じ表で判定する。別の道具で同じことを確認する場合がこれにあたる。扱いの欄に書き足した手順は、判定を通らないまま実行の中に残る。

| 扱い                 | 内容                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| check か撮影に入れる | `.dotagents.json` の `check` か `capture` がその手順を実行するように変える。変更の内容を Issue に書き、起動の前に人が commit する。`/implement` は commit 済みの設定を確かめる |
| 担当を決めて引き継ぐ | workflow の外で行う。完了条件から外して引き継ぎとして書き、誰がいつ行うかを添える。レビューは引き継ぎとして扱い、PR では未検証の項目として残る                                   |
| 今回の範囲から外す   | 完了条件と検証方法から除き、理由を Issue に書く                                                                                                                                  |

## 質問と再評価

未回答・取消や部分的な回答を合意へ読み替えない。回答を得たら、その範囲を記録し、根拠と合意が次の判断に足りるか再評価する。

方針が決まった区切りで、要求・完了条件・検証方法、合意範囲と根拠、未解決事項を Issue・下書きへ反映する。質問ごとの転記や別の正本は作らない。

不足が残れば依存作業を止め、解消後に再評価する。同じ調査・質問で新しい根拠が得られなければ、確認済みのことと必要な判断を示して相談する。
